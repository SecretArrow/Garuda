# Upstream strategy — Motion Browser Chromium fork (spec §70)

## 1. Base revision policy

- Motion pins a single Chromium base revision per fork line. **Current pin:
  `chromium/130.0.6723.58`** (first integration target).
- The authoritative record of *what was actually fetched* is `VERSION_MOTION`,
  generated by `tools/fetch_chromium.sh`. The upstream commit is recorded with:
  ```bash
  git -C chromium/src rev-parse HEAD    # recorded into VERSION_MOTION automatically
  ```
  Treat the recorded 40-hex commit as ground truth; the tag string is documentation.
- Re-fetching the pinned rev later (no-history checkout has no tags):
  ```bash
  git -C chromium/src fetch origin tag 130.0.6723.58 --no-tags
  git -C chromium/src checkout 130.0.6723.58
  gclient sync -D && gclient runhooks
  ```
  (A maintenance machine doing this should use a full-history checkout —
  `fetch android` without `--no-history` — because rebasing, §5, needs history.)
- Pin promotions are deliberate events: they happen on a maintenance machine, are
  validated by a full build + smoke (BUILD_CHROMIUM.md §8), and only then update
  the pin + patch `Base-Revision` headers in a single commit.

## 2. Motion patch series concept

All changes to upstream files are carried as a numbered patch series in
`patches/`, applied by `tools/apply_patches.sh` onto the pristine base revision.

- **Naming:** `0NNN-<area>-<desc>.patch` — e.g. `0003-motion-newtab-default.patch`.
  Numbers are stable identities; never renumber existing patches.
- **Base header:** every patch begins with a mail-style header block carrying:
  ```
  Base-Revision: chromium/130.0.6723.58
  Motion-Patch-Id: 000N
  Motion-Area: branding|package|newtab|bridge|flags
  Verification: NOT verified against a real Chromium checkout — authored against
  the upstream file layout as documented for 130.0.6723.58; paths may drift.
  ```
  `tools/apply_patches.sh` refuses to guess: on conflict it aborts with recovery
  instructions instead of silently skipping.
- **Minimality:** each patch is small, single-purpose, and heavily commented at the
  diff site (`Motion (0NNN): …`) so the next rebase sees intent, not just edits.
- **Prefer args / motion/ tree over patches.** Before touching an upstream file,
  ask: can this be a GN arg (`args.gn`), a runtime hook, or a file in `motion/`?
  Example: package identity lives in `args.gn`; patch 0002 is only a fallback.

## 3. `VERSION_MOTION` file format

Generated at fetch time (`tools/fetch_chromium.sh`), gitignored, read by build
scripts. Canonical shape:

```
# motion-chromium/VERSION_MOTION — GENERATED by tools/fetch_chromium.sh. Do not hand-edit.
chromium_version = "130.0.6723.58"
motion_patch_version = 5
build_version = "130.0.6723.58-motion.5"
upstream_commit = "<40-hex sha from: git -C chromium/src rev-parse HEAD>"
patches = [
  "0001-motion-branding-product-name.patch",
  "0002-motion-package-manifest.patch",
  "0003-motion-newtab-default.patch",
  "0004-motion-agent-bridge-registration.patch",
  "0005-motion-about-flags-agent-toggle.patch",
]
```

- `motion_patch_version` = patch count at fetch time (bumped automatically when the
  series grows; scripts recompute, humans never edit).
- `build_version` feeds `MotionBrowser-<cpu>-<rev>.apk` names and `versionName`.

## 4. Isolation rules

1. **Motion-specific code lives in `motion/`.** Anything we author new (bridge,
   observers, services, UI, native bridge) goes there — including future native
   code (`motion/browser/bridge/*.cc`) and resources.
2. **Upstream files are touched only by the numbered patch series.** No direct
   edits, no extra commits on top of the applied series: a checkout with drift is
   rebuilt, not hand-fixed.
3. **Dep-direction discipline:** `motion_java` must not depend on `chrome_java`
   (patch 0004 wires `chrome_java → //motion:motion_java`). Chrome-side types
   (`TabModelSelector`, `DownloadManagerService`) are reached from the patched
   chrome side or natively, never imported into `motion/`.
4. **No security posture changes** (spec §6): no patch weakens sandbox, site
   isolation, Safe Browsing, TLS verification, or equivalents. Build args change
   identity, not hardening.
5. Every integration point is listed in `motion/README.md` and keeps a
   `TODO(rebase)` marker where upstream internals are known to shift.

## 5. Rebase flow (pin promotion)

```bash
cd motion-chromium

# 1. Fetch the new pinned rev (maintenance box, full-history checkout).
git -C chromium/src fetch origin tag <NEW-VER> --no-tags
git -C chromium/src checkout <NEW-VER>
gclient sync -D && gclient runhooks

# 2. Replay the Motion series onto the new base.
git -C chromium/src checkout -b motion-<NEW-VER> <NEW-VER>
tools/apply_patches.sh            # aborts loudly on the first conflict

# 3. Fix conflicts — ONLY by editing the patch file / motion/ tree.
#    Rule of thumb: if the fix is new code, it belongs in motion/;
#    if upstream reshaped a file, re-shape the hunk minimally.
#    git checkout -m / git apply --reject workflows are fine on the maintenance box;
#    commit the healed result back into patches/ with updated Base-Revision headers.

# 4. Rebuild + smoke (BUILD_CHROMIUM.md §6–§8) before promoting the pin.
tools/gn_gen_android.sh && tools/build_android.sh

# 5. Update VERSION_MOTION + Base-Revision headers in one commit.
```

Conflict policy details:

- Conflicts inside `motion/` are trivial (the tree is ours — port it wholesale).
- Conflicts in upstream files: adapt the Motion hunk to the new upstream shape;
  **never** revert upstream changes to keep our hunk applying (that would silently
  undo upstream security/behavior fixes — a hard violation of §6).
- If an integration point moved (e.g. `WebContentsObserver#onTitleChanged` gained a
  parameter, jni_zero annotation migrated to `org.jni_zero`), port the Motion code
  and update the corresponding `TODO(rebase)` markers.

**Honesty note (spec §77):** these five patches were authored against the upstream

expected to adjust hunks; that is the designed workflow, not a failure.
